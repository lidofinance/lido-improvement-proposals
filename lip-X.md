## Specification

The specification should describe the syntax and semantics of any new feature in enough detail that a competent implementer could build it. There is no fixed sub-structure — organize it however best fits the proposal, for example by subsystem, by contract, or by flow. Common building blocks worth reaching for: an Overview of *how* the LIP solves the problem; a Rationale explaining the reasoning behind the chosen design, trade-offs, and alternatives considered; and a Technical Specification covering the public API of the change. For proposals spanning multiple contracts or subsystems, consider a subsection per contract/subsystem (see LIP-33 or LIP-42 for examples of this style). Test cases for an implementation are expected but may be included with the implementation PR rather than here.
